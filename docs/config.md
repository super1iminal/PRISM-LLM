# Configuration

Settings live in `PRISM-Guided-Learning/configs/`, one folder per tool. The run config says what a run does (domain, dataset, model, planner); the domains themselves are defined in `domains/<name>/`, not here.

| Folder | Used by | Contents |
|---|---|---|
| `run/` | `run_symbolic.py`, `run_ablation.py`, `run_search.py`, `ceilings.py` | `default.yaml` (every key in the table below) and `conditions/<name>.yaml` |
| `ablation/` | `run_ablation.py` | `default.yaml`: `seeds` (default `[1, 2]`; `--seeds` overrides; `--unseeded N` runs N repeats without a seed instead) |
| `experiments/` | `run_experiment.py` | one file per research-question experiment (`rq1_comparison.yaml`, `rq2_*.yaml`); keys and the run store in `docs/experiments.md` |
| `transfer/` | `transfer.py` | `default.yaml`: `workers` (target instances checked in parallel; `--workers` overrides), `exact_near` (re-check with the exact solvers when a worst case is this close to its threshold), `sealed` (dataset -> sealed test target ids; `transfer.py` and `run_baseline.py` refuse them without `--unseal`) |
| `baselines/` | `run_baseline.py` | one file per baseline run (method, run condition for the rule language, dataset, training and target ids, method parameters); keys in `baselines/README.md` |

- `run/conditions/<name>.yaml`: one file per named run condition (B1, B2, R1–R5, D7, S1, S4, S5, V1, V2, L1, L2, U1, `pre_phase_a`), each a small override of the default, selected with `--condition <name>`. A new kind of run gets a new file. B2 and the conditions compared with it set `planner.retry: "stall:2"`.
- Each folder's `default.yaml` is the only place its defaults live: the schemas (`src/config.py` for the run, a dataclass in each tool) have none, so a missing key is an error, as are unknown keys and unsupported values. Tools take `--config FILE` and `--set key=value`.
- Every run writes its resolved config to `<run>/config.json`. Reports and figures read a run's dataset, model and round budget from there (`src/results_io.py`), so plot configs never repeat them. Runs without a `config.json` (the single-seed runs) read as a fixed record of their settings (gridworld, `grid_20_balanced.csv`, 5 rounds, qwen3:14b).

```bash
python src/run_symbolic.py --condition R2 --set run.limit=1 --set llm.seed=1
```

```bash
python src/run_ablation.py B2 R1 R2 R3 R4 R5
```

| `feedback.blame` | `mass` | blame signal: `mass`, `regret` (one-step regret, no occupancy), `random` (placebo), `none` (no blame section) | S5, V1, V2 |

| `feedback.trajectory` | `false` | also show one likely way the rules fail (a trace from the start) in REFINE/EXTEND prompts | previous loop |
| `feedback.early` / `early_tolerance` | `null` / 0.01 | a step counter (Pac-Man: `steps`): score the rules' move in every decision state of the first half of each training game (any play reaches it) against the best move there (`src/core/early.py`); keep-best prefers the lower mean loss after the training score, and once the members pass the loop keeps refining (EARLY prompt) while the mean loss exceeds `early_tolerance` (1: stop at the first passing list) | `haiku_pac_early`, `haiku_pac_narrow*` |

| `feedback.space` | `states` | how feedback (blame, uncovered hotspots, the failing trace) names states: `states` (their valuations) or `features` (boolean variables, state features (`name=value` if integer, e.g. Pac-Man's `moves_left`) and, per action, the action features that hold; integer variables such as positions and headings are left out). | `feedback.stuck` | `false` | at those states, say which of the rules' actions change nothing there (every outcome is the state itself, e.g. MER's disabled actions), so the run stays there forever | `haiku_*_optfb_stuck` |

| `feedback.history` | `false` | with `planner.feedback: failures`: a state whose own variables show a requirement already met is neither lost nor a failure there (`Domain.met`). | `prism.method` | `gaussseidel` | PRISM solver; plain value iteration fails on periodic chains (rules that read `obs_idx`) | — |
| `prism.fallback_methods` | `[modpoliter]` | tried in order when `method` does not converge (seen on a real qwen rule set) | — |
| `prism.multi_engine` / `multi_method` | `sparse` / `lp` | joint queries (the explicit engine can't do them; LP is exact) | — |
| `prism.java_max_mem` / `max_iters` / `timeout_s` | 4g / 1,000,000 / 900 | PRISM limits | — |
| `prism.max_concurrent` | 8 | PRISM processes at once on the whole machine, across every run, session and tool (half of the 16 logical cores, so Asher keeps CPU; Asher, Oct 15). A call in place waits for a slot; the event and lockstep schedulers keep a waiting call queued and go on. `null`: no cap. The run store ignores it | — |
| `prism.exact_check` | `true` | re-verify the final policy with the exact solvers (`prism.exact_methods`); the run reports those values (the loop's are kept as `loop_best` / `loop_worst`). Runs whose `config.json` has no `exact_check` report the loop's values | — |
| `prism.exact_methods` | `[intervaliter, lp]` | the exact solvers, tried in order, of the final check, `src/transfer.py`'s re-check near a threshold, `src/recertify.py` and the sequential study (`core.verifier.exact_solvers`), then Gauss-Seidel at `exact_fallback_epsilon`. The run store ignores the exact solvers' settings: they change no choice of the loop | — |
| `prism.lp_tolerance` / `ii_max_iters` | 1e-3 / 1,000,000 | linear programming differed from interval iteration by up to 1.0e-4 over ~300 checks, so a margin within `lp_tolerance` of a threshold is inconclusive (`core.verifier.exact_verdict`; `src/recertify.py reverdict` re-applies it to written checks); interval iteration's iteration cap before linear programming (~7 s on 1-2k states) | — |

| `rules.shared_literals` | `false` | with `general`: other numbers too, but only in comparisons over the variables whose range is the same on every training member (Pac-Man: positions and headings, not `steps`) | `haiku_pac_literals`, `haiku_pac_early` |

| `rules.extra_features` | `[]` | optional domain features to include; a domain marks a feature `optional` when older runs never had it, so their prompts stay the same (gridworld: `collide`, the move or a slip of it can end where the moving obstacle goes next) | `haiku_fam_collide*` |
| `rules.strict` | `false` | conditions may not name what the domain withholds (`Domain.strict`: gridworld, the coordinates and the grid and goal constants; Pac-Man and MER, sums of number literals such as `1 + 1`); the prompt leaves those names out and an answer that uses them is rejected (re-asked with the error) | `port_*` |
| `rules.any_order` | `none` | `rotations` / `all`: each round, `any` rules are resolved into the action order (rotations of the declared order, or all permutations) that does best on the members; `declared`: always the declared order; `report`: worst case, the best order only named in the feedback; `none`: worst case over the allowed actions (`docs/semantics.md`) | `rq2_choices` |
| `rules.any_scorer` | `prism` | what scores the orders of `rules.any_order`. `prism`: each order is verified with PRISM (an order that resolves the rules into the same model as one already verified takes its values, which changes nothing). `domain`: the domain's fast model scores every order (gridworld: the numpy model, `src/baselines/gridworld_mdp.py`) and PRISM verifies only the chosen one; it picks another order than PRISM on near-ties (about half the recorded rounds), so the run store counts it. Where the rules leave a reachable state open, PRISM scores the round | — |
| `rules.any_prune` | `false` | the domain's fast model rules out the orders that cannot score best whatever PRISM's solver error (up to 1e-3), PRISM verifies the rest, and all of them if a verified order is off by more. The same order as without it on every recorded round (`DECISIONS.md`), with fewer PRISM checks, so the run store ignores it. Domains without a fast model (Pac-Man) verify every order | — |
| `legacy.max_rounds` | 5 | legacy rounds; with `obs_idx` visible, one call per (goal, obstacle phase) | — |
| `legacy.retry` | `never` | `stall:k`: after k rounds without improvement, the next round uses the initial prompt | L1 |
| `legacy.examples` | `true` | the two worked examples in legacy's initial prompt | L2 |
| `run.workers` / `run.limit` | 2 / `null` | instances in flight (worker threads, the lockstep batch size, or the event scheduler's slots and concurrent LLM requests) / first N instances only | — |
| `run.train_sets` | `[]` | symbolic only. Groups of instance ids (dataset rows): one rule set per group, written for and verified on every member each round, solved only when every member passes (`core/training.py`, "Training sets" in `semantics.md`). Certify the frozen rules on held-out instances with `src/transfer.py`. `[]`: one rule set per instance | —, `port_uuv_sets` (three UUV sets) |
| `run.hidden_sets` | `[]` | per training set, further instance ids verified and scored every round (keep-best, done) but never shown to the LLM; the prompt only says on how many the rules hold | previous loop |
| `run.pool_sets` | `[]` | per training set, candidate ids: once the set is solved, the first on which the kept rules fail joins it (counterexample-driven training sets) | previous loop |
| `run.scheduler` | `null` (symbolic: `event`; legacy: `threads`) | `threads`: each worker solves an instance, calling the LLM and PRISM itself. `lockstep`: every step sends one task per active instance as one batch; between batches the instances' PRISM calls run as parallel processes. `event`: each instance moves on as soon as its own LLM result or PRISM output arrives. `lockstep` and `event` run all planner code in one thread, log their tasks to `<run>/llm_tasks.jsonl` and drive the symbolic planner only. See `docs/scheduler.md`. With Ollama, concurrent requests only run in parallel if `OLLAMA_NUM_PARALLEL` ≥ `run.workers` | — |
